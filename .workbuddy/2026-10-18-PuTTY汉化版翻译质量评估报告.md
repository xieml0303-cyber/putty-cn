## 1. 评估方法与口径

### 1.1 方法

1. **历史记录检索**：核对项目记忆、`docs/` 各轮改造报告与 git 提交历史，确认汉化来源与既往改动边界。
2. **全量字符串提取**：用脚本按 C 字符串字面量提取全部含 CJK 字符的字符串，按文件统计分布；同步提取 `ctrl_*` 界面调用中仍为纯英文的参数，识别漏译。
3. **人工逐条比对**：以 PuTTY 0.85 上游英文源码为基准，对配置面板、运行时消息、菜单、命令行帮助逐条比对语义。
4. **结构化检查**：统计半角标点、中英混排空格、省略号用法；按 `shortcut_escape()` 的实现逻辑检查助记符字母是否存在于标签文本中。

### 1.2 判定口径

- **P0 语义错误**：译文与原文语义相反、指代错误或丢失关键限定词，可能导致用户选错配置或误判连接状态。
- **P1 一致性与完整性**：术语不统一、界面英文残留、助记符失效、错别字或非原文内容混入。
- **P2 表达与格式**：翻译腔、标点空格不规范、与当前定制不一致，不影响功能但影响专业观感。
- **不计入问题**：协议名、算法名、产品名保留英文（SSH、Telnet、AES、ChaCha20、SOCKS 5、ClearType 等）；`unix/config-gtk.c` 的 GTK 界面（Windows 交付物不加载）。

## 2. 总体结论

1. **主体可用，但存在会误导操作的硬错误。** 配置面板与主界面完成度高，日常使用不受阻；但 22 处语义错误中有 4 处属于“勾选效果与字面意思相反”级别，必须优先修正。
2. **错译集中在协议术语。** `keyboard-interactive`、`MORE`、`ignore messages`、`line drawing`、`code points`、`logical name` 等被当作普通英语意译，是 P0 问题最密集的来源。
3. **术语缺统一表。** 同一概念存在 2–4 种译法（串口、线条绘制、算法优先级、伪终端、事件日志等），说明汉化是按文件推进、未做全局术语收敛。
4. **漏译呈“半成品”分布。** 同一代码路径中英混杂：`windows/putty.c` 已有“未知选项”却仍保留 5 条英文错误；`network.c` 主机名解析三条错误全英文；`config.c` 夹着一条完整英文复选框。
5. **9 处助记符实际失效。** 中文标签内不含对应拉丁字母，`shortcut_escape()` 无法插入 `&`，括号里的字母提示成为无效装饰。
6. **`pscp`/`psftp` 基本未汉化**，`cmdgen`/`plink` 命令行错误大量保留英文。若这些组件在交付范围内，需单独立项。

### 4.3 回归验证要点

## 5. 附录

### 5.1 统计口径

- 中文字符串：C 源码中字符串字面量含 `U+4E00–U+9FFF` 的项，含跨行拼接的单个片段。
- 文件统计排除 `src/doc/`（文档源，非界面文本）与 `build/`（中间产物）。
- 漏译识别：`ctrl_*` 界面调用参数中不含中文且非纯符号/协议名的字符串；`ctrl_getset` 的面板 key 参数不计。
- 助记符检查：取标签后首个字符常量作为 shortcut，判断其是否出现在标签文本（忽略大小写）中。

- 终端内运行时输出（服务器返回内容）：不属于界面汉化范围。
