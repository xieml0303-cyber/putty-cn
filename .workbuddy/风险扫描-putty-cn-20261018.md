### 8.2 对正文判断的更正

**更正一：M1 由「中」降为「低（理论风险）」。**
正文的推理前提是「同时打开两个配置框」，但 PuTTY 每个会话运行在独立进程中，配置框为模态窗口；初始配置框未关闭时无法再进入「修改设置」，跨进程时文件级 static 各自独立。`src/config.c:1783`（`} serial_ui;`）确为文件级 static，但不存在可达路径造成 `ctrl` 与 `dlg` 分属不同对话框。建议保留「挂到对话框上下文」的整改方向，但不必按「中」优先处理。

**更正二：M2 由「中」降为「低」。**
正文称「换一个会话后下拉框仍显示上次的厂商名」，但 static 变量不跨进程，新会话必然重置。真实场景仅剩同一进程内「修改设置 → 取消 → 再次修改设置」；且六家厂商参数完全一致，错的只是显示名，不影响实际串口参数。`src/config.c:1786`（`static int serial_standard_last = -1;`）属实，影响面按低处理。

正文称「打开配置框再点打开就可能连错设备」。实际 `fill_serial_port_list()` 在 `src/config.c:217-222` 的 `if (!present && nports > 0)` 分支中，不仅改写界面文本，还调用 `conf_set_str(conf, CONF_serline, saved)` 写回内存中的 Conf。用户若在此状态下点「保存」，错误端口会被持久化进默认设置或具名会话，下次启动直接沿用。整改时除「保留原值 + 可见提示」外，还须覆盖保存路径，避免把回退值当作有效配置落盘。
