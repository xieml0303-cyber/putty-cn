# 终端重排「没生效」排查与拖动实时重排

日期：2026-10-21

## 一、为什么看起来没生效

重排代码（`src/terminal/terminal.c` 里的 `reflow_buffer()` 及 `term_size()` 中的重排分支）
上一轮就已经实现并通过单元测试，问题不在代码逻辑，而在**跑的是旧程序**。

`dist/` 下的 `putty.exe` 等产物生成于源码改动之前，用的是旧二进制：
源码里改了 `terminal.c`，但没有重新构建 `dist`，所以双击运行时行为依旧是「缩放后
内容被截断/丢字」，看起来就像重排完全没做。

核对方法：

```
nm dist/putty.exe | grep defer_backend      # 改前无输出
nm dist/putty.exe | grep defer_backend      # 改后有 term_set_defer_backend_size
```

现在 `dist/putty.exe`（及 pageant/plink/pscp/psftp/puttygen/puttytel）已重新构建，
时间戳晚于源码，符号检查通过。**必须用新 `dist/putty.exe` 测试**。

## 二、顺带补上的「拖动中实时重排」

原来的路径是：拖动过程中 `WM_SIZE` 只更新窗口尺寸，`term_size()` 要到松手
（`WM_EXITSIZEMOVE` 之后）才执行一次。表现是拖动时文字不动，松手瞬间才重排，
手感上像"卡一下才生效"。

改动三处：

**`src/terminal/terminal.h:445`** — `Terminal` 增加 `bool defer_backend_size`。

**`src/terminal/terminal.c:2737`** — `term_size()` 里通知后端的那一步变成条件执行：

```c
if (term->backend && !term->defer_backend_size)
    backend_size(term->backend, ...);
```

配套 `term_set_defer_backend_size()`（`terminal.c:2746`）在标记翻转时补发一次
最终尺寸，保证不会漏掉通知。

**`src/windows/window.c:2196`** — `wm_size_resize_term()` 在 `wgs->resizing`
期间每次尺寸变化都跑完整的 `term_size()`（含重排）并 `InvalidateRect` 立即重绘；
`WM_ENTERSIZEMOVE`（`window.c:2974`）打开延后标记，`WM_EXITSIZEMOVE`
（`window.c:2985`）关掉它。

这样拖动中每帧都能看到重新折行，而对端服务器全程只收到松手后的那一个最终尺寸，
来回拖也不会刷一串 window-change 请求。

## 三、验证

新增一段模拟拖动的回归测试（`src/test/test_terminal.c`，插在「多宽度往返」之后）：

- 以 80 列为起点，连续 60 次按 ±2 抖动宽度（夹在 12..120），每次 `term_size()`
  后断言全缓冲区（含 scrollback）非空白字符数恒为 100；
- 抖动结束后回到 80 列，断言字符数仍为 100、首行末格是 `a`、光标落在 (1,20)。

这条用例专门抓「反复 resize 累积丢字/重复」这一类问题——正是拖动场景的真实形态。

全部既有用例（窄化/加宽重排、多宽度往返、宽字符不劈半、scrollback 参与重排、

## 四、需要人工确认的部分

自动化测不到「肉眼看到的折行」这一层。请用新的 `dist/putty.exe` 连一个会话，
输出一段超过窗口宽度的长行（例如 `ls -l` 长路径、或 `cat` 一个长 JSON），然后：

1. 拖窄窗口 —— 文字应随拖动过程持续重新折行，而不是松手才跳一下；
2. 拖宽窗口 —— 之前折成多行的内容应拼回长行；
3. 窗口缩到很窄再拉回原宽 —— 内容字符不应丢失、不应出现重复段。

第 3 条是本次重点：如果仍看到丢字，那问题在 `term_size()` 的边界条件而非构建，
请把当时的宽度变化过程和大致内容长度记下来。
