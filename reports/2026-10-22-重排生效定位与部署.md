## 六、拖动过程中不实时重排的修复

把程序换成新构建后，用户反馈仍有问题：窗口缩放要松手了内容才更新，
拖动中文字不动。

### 根因

`term_size()` 结尾只调 `term_schedule_update(term)`，它把 `term_update_callback`
塞进 toplevel 回调队列（`terminal.c:1336`）。而 `run_toplevel_callbacks()` 只在
`gui_main_loop()` 的主消息循环里被调用（`window.c:889`）：

```c
    while (GetMessage(&msg, NULL, 0, 0)) {
        ...
        run_toplevel_callbacks();
    }
```

拖动窗口边框时，Windows 进入自己的 modal 尺寸调整循环，消息直接派发给 WndProc，
**永远不会回到 `gui_main_loop()`**。于是：

1. `WM_SIZE` → `wm_size_resize_term()` → `term_size()` 完成了重排，
   但 `disptext` 还是旧的（`term_update` 没跑）；
2. 原来的 `InvalidateRect(wgs->term_hwnd, ...)` 触发 `WM_PAINT`，
   `do_paint()` 画的是**旧的 `disptext`**，看上去毫无变化；
3. 松手 → `WM_EXITSIZEMOVE` → 回到主循环 → 回调终于执行 → 内容才更新。

这就是「松手才重排」的机制，跟重排算法本身无关。

### 修复

`src/windows/window.c` 的 `wm_size_resize_term()` 里，`resizing` 分支把
`InvalidateRect` 换成同步的 `term_update(wgs->term)`：

```c
    term_size(wgs->term, h, w,
              conf_get_int(wgs->conf, CONF_savelines));
    if (wgs->resizing) {
        term_update(wgs->term);
    }
```

`term_update()` 末尾会直接 `do_paint(term)`（`terminal.c:1559` 附近），
不依赖消息循环，所以拖动中每帧都能看到重新折行。对端服务器仍然只在松手时
收到一次最终尺寸（`defer_backend_size` 机制不变）。

### 验证

先试过用 `SetCursorPos` + `mouse_event` 模拟真实拖拽，结果 `GetWindowRect`
在拖动中途仍返回原宽度（505px），松手后才变成 265px —— 说明程序化移动
触发的是 Windows 的轮廓模式，没有真正 resize，这条路证明不了任何东西，
记录在此以免下次再走弯路。

换成能确定性进入 `resizing` 状态的时序（`reports\reflow-modal-e2e.ps1`）：

1. 启动程序连本地假服务端，等 6 行长文本渲染完；
2. `SendMessage(WM_ENTERSIZEMOVE)`，与拖动时同一状态；
3. `MoveWindow` 把宽度砍半；
4. **不 sleep，立刻 `PrintWindow` 截图** —— 这个间隙里 toplevel 回调
   不可能跑完；
5. `SendMessage(WM_EXITSIZEMOVE)` 收尾。

结果：mid 截图（252×497）内容已经是重排后的 5 行折行形态
（`reflow-fixed-mid.png`）。若没有同步 `term_update`，此刻 `disptext`
仍是旧的，截图会是重叠错乱的窄窗口。

部署到 Program Files 后用同一脚本复验，`reflow-pf-mid.png` 同样正确。

新构建 md5：`9DA81F49F66A59DA0B887DFC56393EBC`，`src/build`、`dist`、
`Program Files` 三处一致。

## 七、最终真相：系统关闭了「拖动时显示窗口内容」

代码修好后用户仍反馈拖动不实时。查系统参数发现：

```
SPI_GETDRAGFULLWINDOWS = 0     ← 实际生效值是 0（关闭）
HKCU\Control Panel\Desktop\DragFullWindows = 1   ← 注册表却写着 1，是假象
```

`DragFullWindows = 0` 意味着拖动边框时 Windows 只画一个虚线轮廓框，
**窗口本身不改尺寸、不发 `WM_SIZE`**。推论很硬：

- 没有 `WM_SIZE` → `wm_size_resize_term()` 不被调用 → `term_size()` 不执行
  → 重排代码根本没机会跑；
- 松手后系统才 `SetWindowPos`，这时才有一次 `WM_SIZE`，于是"松手才重排"。

这解释了为什么所有程序化验证（`MoveWindow`）都通过、真实拖动却无效——
程序化改尺寸绕过了拖动模式，直接触发 `WM_SIZE`。

### 把设置打开

坑在于 `SPI_SETDRAGFULLWINDOWS` 的两种调用写法只有一种生效：

```csharp
// 无效：按 MSDN 描述传 BOOL* 到 pvParam，返回 True 但值不变
SystemParametersInfo(0x0025, 0, &flag, 0x03);

// 有效：值走 uiParam，pvParam 传 NULL
SystemParametersInfo(0x0025, 1, NULL, 0x03);   // 0x03 = UPDATEINIFILE|SENDCHANGE
```

执行后：

```
SPI_GETDRAGFULLWINDOWS now = 1
registry DragFullWindows = 1
```

排查过程里也确认了不是远程桌面：`SESSIONNAME=Console`、`SM_REMOTESESSION=0`，
本地会话，所以该设置本应可用，只是被关掉了。

### 真实鼠标拖动复验

用 `mouse_event` 在窗口右边框按下并分 6 步左移，鼠标仍按住时截图
（`reports\reflow-drag-e2e.ps1`）：

| 阶段 | 窗口 | 内容 |
| --- | --- | --- |
| 拖动前 | 545×497 | 每逻辑行折 2 行 |
| 拖动中（按住） | 385×497 | 每逻辑行折 3 行，字符连续无缺 |
| 松开后 | 305×497 | 折行继续跟随 |

对比同一脚本在设置打开前的运行结果：mid 阶段窗口仍是 505×497 且内容未变，
差别一目了然。截图：`reflow-real-mid.png`。

**结论**：实时重排需要两件事同时成立——PuTTY 侧的同步重绘（第六节），
以及系统侧的「拖动时显示窗口内容」（本节）。缺任何一条都表现为"松手才更新"。

## 八、附：本轮踩到的脚本坑

`deploy-putty-reflow.ps1` 第一版含中文注释，运行直接以退出码 1 失败且不产生日志。
原因是 Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按系统 ANSI（GBK）解码，
UTF-8 中文字节把字符串引号吃掉了，报「字符串缺少终止符」。改成纯 ASCII 后正常。
以后写 `.ps1` 一律避免非 ASCII 字符，或显式写入 BOM。
