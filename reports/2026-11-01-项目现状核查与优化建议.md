## 二、工程卫生（优先级最高的三项）

### 2.1 行尾污染：24,756 行假改动

实测 `git diff --stat` 报 24,756 增 / 24,756 删，而 `git diff --ignore-all-space --stat` 输出为空——**没有任何真实代码改动，纯粹是 LF 被改写成 CRLF**。

逐文件去 CR 后与 `HEAD` 比对，30 个文件全部是「纯 CRLF」：

| 类别 | 文件 |
|---|---|
| 源码 | `src/config.c`、`src/dialog.c`、`src/dialog.h`、`src/terminal/terminal.c`、`src/test/fuzzterm.c`、`src/test/test_terminal.c`、`src/unix/dialog.c`、`src/windows/controls.c`、`src/windows/jump-list.c`、`src/windows/README-msi.txt` |
| 配置 | `.gitignore` |
| 报告 | `reports/2026-10-18-M3-M4-M6整改与完整审计.md`、`…命令行工具汉化完成报告.md`、`…工作区迁移核对与补齐.md`、`…翻译质量修复与回归报告.md`、`…2026-10-30-连接类型下拉框暗淡化改造.md`、`串口下拉框-点击任意位置展开-报告.md`、`串口下拉框只读-验证报告.md`、`风险扫描-putty-cn-20261018.md` |
| 文档 | `docs/` 下 9 份 |
| 测试 | `tests/quick-test.ps1`、`tests/read-error.ps1`、`tests/test-putty.ps1` |

根因：仓库既无 `.gitattributes`，`core.autocrlf` 也未设置，行尾完全取决于最后一次写文件的工具。某个在 Windows 上运行的编辑或复制动作把整文件重写成了 CRLF。

危害是具体的：本项目的审计链依赖提交哈希溯源（风险扫描报告每条结论都挂 commit），一旦这 2.3 万行噪声进库，后续 `git log -S` 查某行代码的来历会命中错误提交，`git blame` 也失真。

处置建议（三步，按顺序）：

```bash
# 1) 先还原纯行尾差异的文件（先确认没有夹带真实改动）
cd C:/Users/Wrok/Repos/putty-cn
for f in $(git diff --name-only); do
  if diff -q <(git show "HEAD:$f") <(tr -d '\r' < "$f") >/dev/null; then
    git checkout -- "$f"
  fi
done

# 2) 固化行尾策略，防止复发
printf '* text=auto eol=lf\n*.ps1 text eol=crlf\n*.bat text eol=crlf\n*.exe binary\n*.png binary\n' > .gitattributes
git config core.autocrlf false

# 3) 验证：应该只剩真实改动
git diff --stat
```

注意 `.ps1` 用 CRLF 是刻意的——Windows PowerShell 对纯 LF 脚本的历史兼容性不佳，而归为二进制的 `.exe/.png` 必须绕开文本处理。

### 2.2 README 哈希表已全线失真

README「免安装版」表的八条哈希与 dist 实测逐条不符：

| 文件 | README 记录大小 | 实际大小 | 结论 |
|---|---|---|---|
| putty.exe | 1,845,159 | 1,862,029 | 不符 |
| puttygen.exe | 902,380 | 912,067 | 不符 |
| plink.exe | 1,416,971 | 1,418,311 | 不符 |
| pscp.exe | 1,414,811 | 1,416,663 | 不符 |
| psftp.exe | 1,430,258 | 1,432,110 | 不符 |
| pageant.exe | 756,950 | 758,229 | 不符 |
| puttytel.exe | 961,969 | 979,863 | 不符 |
| 安装包 | `b4af2028…` | `1705d704…` | 不符 |

连大小都对不上，不只是哈希——说明这张表停在 10-18 那次发版，之后 10-30 的重打包完全没回填。

这里有个方法论问题值得写进 README：**哈希不能用于跨构建比对**。PE 头里嵌了链接时间戳，同一份源码两次构建必然不同（实测 dist `6cce5af7…` vs `src/build` `1581c446…`，功能一致）。所以哈希表的正确用法是「校验下载完整性」，而不是「判断是不是最新版」；判断版本应看 `plink -V` 的输出。README 里最好把这句话写清楚，否则每次重打包后都有人（包括未来的自己）纠结为什么哈希变了。

### 2.3 验证脚本被挡在库外

`.gitignore` 第 27–31 行把 `reports/*.py`、`reports/*.ps1`、`reports/*.png`、`reports/*.log` 全部排除，理由是「只保留 Markdown 报告」。结果：

- 磁盘上 19 个 `verify_*.py`、39 个 `.ps1`、105 张截图、34 个 `.py` 诊断脚本全部不入库；
- 而报告里反复引用这些脚本作为证据（例如《串口跨行退格修复》引用 `reports/verify_del_bytes.py`）。

矛盾在于：**报告要可复核，复核手段却不在库里**。clone 一份仓库，所有「用 A/B 注入法实测通过」的论断都无法复现。

建议分两类处理：

- 判定性脚本（`verify_del_bytes.py`、`verify_apply_keepopen.py`、`verify-ruled-list*.py` 这几个报告直接引用的）移入 `tests/gui/`，纳入版本控制——它们本质是测试资产，不是临时诊断；
- 一次性诊断脚本与截图继续留在本地，但在报告里把引用改成「方法描述 + 脚本名」，并注明脚本仅本地留存，避免读者去找一个不存在的东西。

## 三、仓库体积与分发

dist 的八个二进制全部入库，历史累计 **39 个 dist blob、56.2 MB**（已去重），当前 `.git` 24 MB。每次重打包都会新增一份 3 MB 安装包 + 约 8 MB 的 exe 集合，且二进制几乎不可压缩，仓库只会单向变大。

现在的取舍可以理解：dist 入库让「直接下载仓库里的 exe」成为可能，README 也在用这个点做卖点。但代价是 clone 越来越慢，而 GitHub Release 的下载体验其实更好（有 CDN、有版本历史、有 checksum）。

折中方案：仓库只保留**当前版本**的 dist（也就是维持现状，但每次发版时删掉上一版的二进制而不是累积），历次产物全部走 Release。如果愿意做一次历史清理（`git filter-repo` 剔除历史 dist blob），能把 `.git` 从 24 MB 压到 3 MB 量级——但这会改写全部提交哈希，**与 §2.1 的审计溯源诉求直接冲突**，因此不建议在当前阶段做。等发 cn3 时顺势把这事定下来更划算。

另外两个可以立刻清掉的：`build/`、`build2/` 各 17 MB 的构建残留（已被 gitignore，删除无风险），以及 `src/build/putty_old.exe`（10-27 的旧构建，1.8 MB，容易误运行）。

## 四、构建与验证的工程化

这是我认为**长期回报最高**的一项。

当前每轮闭环依赖一套口口相传的操作序列：`env PATH=… ninja putty.exe` 的 PATH 绕坑、`ninja test_terminal`、GUI 脚本手工跑、`cp` 同步 dist、`ISCC` 打包、`gh` 发版（还要先 export 代理）。这套流程现在只存在于记忆文档里，换个人接手就要重新踩一遍四个构建坑。

建议做三件小事：

第一，落一个 `build.ps1`（或 `build.cmd`），把 PATH 修正、目标列表、rc.obj 清理（坑 3 的 version.rc2 陷阱）固化进去。参数化 `-Target putty,plink -Clean`，这样「改版本号忘记删 rc.obj」这类错误从流程上消失，而不是靠记性。

第二，把 `ninja test_terminal` 等 14 个测试目标接入 ctest——现在源码里有 `add_executable(test_*)` 14 处，但**没有任何 `add_test` 注册**，等于测试得靠人手动跑、手动读退出码。加一层 `add_test` 就能让 `ctest` 一把过，也为 CI 铺路。

第三，加一个最小的 GitHub Actions：`windows-latest` + MSYS2 + cmake + ninja，只跑「能构建 + ctest 通过」两件事，不做打包。这条流水线的价值不在当前 790 个文件能不能编过（肯定能），而在于**未来任何一次改动都能立刻知道有没有把人家的构建搞坏**。当前仓库完全没有 CI。

## 五、版本与发版

版本串 `0.85-cn2` 同时写在四处：`src/version.h`（`TEXTVER`、`SSHVER`、`BINARY_VERSION`）、`src/LATEST.VER`、`installer/putty-cn.iss` 的 `MyAppVersion`，以及 README 标题。四处手工同步，天然容易漏。

现状是 tag 停在 `75e1e6c`，代码已前进 **22 个提交、25 个文件、+2464/−350 行**，而 dist 与 Release 资产已经重打包为含全部改造的版本——于是出现了一个尴尬的状态：**用户下载到的安装包里装着 cn3 的功能，标签却写着 cn2**。

两条路，选一条：

- 发 cn3：升四处版本串 → 按坑 3 删两组 rc.obj 重编 → 重打安装包 → 更新 README（哈希 + 改动表）→ 三处对齐核对（远端 main sha / tag sha / 资产 digest）。这是常规路线。
- 或者把 cn2 定义为「滚动版」，tag 不再代表内容边界——但这会让 Release 页失去版本语义，不建议。

顺带修掉 README「相对上游的改动」表：它只列了 6 个文件，而 cn2 之后实际动了 `terminal/terminal.c`、`windows/serial.c`、`pscp.c/psftp.c/cmdgen.c`、`windows/window.c`（单文件 599 行 diff）等。把表补全到「文件 + 一句话职责」的粒度，接手的人和用户都能对上号。

## 六、源码层面的观察

只做了抽样，未做完整审计，以下三条是读代码时注意到的。

**串口回退的 H3 仍未决。** `src/config.c` 的 `fill_serial_port_list()`（实测在 :211 起，文档记的 :217 已漂移）在发现保存的端口不在本机列表时，直接 `conf_set_str(conf, CONF_serline, saved)` 写回内存 Conf——用户此刻点「保存」，这个自动回退值就永久落盘。更隐蔽的是第二段：保存的是蓝牙口而插上了物理口时，也会静默改写成物理口。两条路径都没有任何提示。这在「换机器用同一个注册表配置」的场景下会让用户莫名其妙地连不上设备。可选策略还是那两个（保留原值 + 提示 vs 禁止回退），但**至少应该有一条可见提示**——静默改写用户配置是这一条里最扎眼的地方。

**`strip_port_suffix()` 用字节串截断处理 UTF-8。** 它靠 `strstr(s, "（")` 找到全角括号再把字符串截断。功能上没问题（全角左括号的 UTF-8 首字节不会出现在合法多字节序列的中间），但这是隐式的编码假设。若将来有人换了后缀格式（比如改成半角括号或冒号），这里会静默失效。值得补一条注释，说明「依赖 UTF-8 首字节不重叠」这个前提。

**`ruledlines` 的自绘路径依赖字体实际高度，但隔离是干净的。** `windows/controls.c:956` 起的 `listbox()` 里，行高是从 `GetTextMetrics` 实测而非常量，这个做法是对的（注释也写了「否则文字被裁」）。原本担心开启 `LBS_OWNERDRAWFIXED` 会波及全站列表框，实测核对后可以消除：`ruledlines` 在 `src/dialog.c:358` 统一初始化为 `false`，全仓库只有 `src/config.c:2258` 一处把它置 `true`（会话历史列表），`windows/controls.c:1871` 是唯一读取点。也就是说自绘路径只对历史列表生效，其他 10 个 `ctrl_listbox()` 调用点照旧走原生绘制。**这一条无需改动，记录在此以免后来者重复怀疑。**

## 八、建议的执行顺序

如果只做三件事，按这个顺序：**先修行尾（§2.1），再刷新 README 哈希（§2.2），然后发 cn3（§5）**。三件加起来一天内能完成，且能立刻消掉「仓库状态不可信」和「版本语义不清」两个根本问题。

之后按周的粒度推进工程化：`build.ps1` → `add_test` + ctest → GitHub Actions。这三件做完，这个项目就从「靠一个人的记忆维持」变成「换谁都能接手」。

最后说一句题外话：这个项目的技术记忆文档质量相当高（构建四坑、GUI 验证十坑、串口测试床的选择理由都写得很扎实），这本身就是最大的资产。上面所有建议的共同指向是——**把记忆里的东西变成机器能执行的东西**，因为记忆会漂移，脚本不会。

### 9.2 更正：「30 个文件 24,756 行假改动」当前不成立

- 实测 `git status --short` 仅有 3 个未跟踪项（`.v2c/`、本报告、`reports/会话日志功能代码梳理.md`），`git diff --stat` 与 `git diff --ignore-all-space --stat` **均为空**——当前不存在待提交的行尾假改动。
- 根因：本机全局配置 `core.autocrlf=true`（来源 `C:/Program Files/Git/etc/gitconfig`，系统级，非仓库级）。checkout 时 LF→CRLF、commit 时 CRLF→LF，索引层自动归一化，因此工作区文件虽为 CRLF 也不产生 git diff。原报告 §2.1 所称「git diff --stat 报 24,756 增/删」在本机当前状态**无法复现**；工作区 30 个文件为 CRLF 属实，但在 autocrlf=true 语义下不构成 git 层面的假改动。
- **原建议仍然成立且更必要了**：仓库无 `.gitattributes`，行尾行为完全依赖本机全局配置；一旦配置变更、换机或引入不做归一化的工具，假改动风险立即显形。建议把原三步方案中的「还原文件」一步改为「直接提交 `.gitattributes` 固化策略」（属新增改动，当前没有需要还原的文件）。
